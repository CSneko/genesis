# QQ conversations and people

English | [中文](qq.zh.md)

## Summary

The optional [QQ layer](../../packages/experimental/genesis-qq/README.md) connects an already initialized Genesis life to OneBot 11 conversations. Each group and private conversation has its own durable Harness Session; one QQ account identifies the same person across them. Relationship estimates never grant permissions.

## Connect from this workspace

Configure and name the life through the [awakening flow](awakening.md). Run a OneBot 11 client such as SnowLuma separately and log into a dedicated bot account yourself. Use the same access token on both ends; keep credentials outside Git and chat messages.

Start this workspace through the supported entry point. Its Genesis composition includes QQ settings with the connection initially disabled:

```sh
pnpm dsh web
```

1. Open **Plugins → Genesis → QQ**. Save an access token of at least 16 characters without whitespace; the existing credential provider stores it under `GENESIS_QQ_TOKEN`, and the page never receives its value.
2. Enter the bot account and optional verified operator account. For a forward connection, enter a local endpoint such as `ws://127.0.0.1:3001`. For a reverse connection, leave the endpoint empty and set the listener port; the default is 6700.
3. Enable QQ connection and choose **Save and apply connection**. Check the sampled status; if connection fails, check the OneBot client and token, then save again to retry. Refresh to read the latest status.
4. Set allowed groups and private correspondents under **Conversation access**, then save. Separate IDs with commas or spaces. Empty lists refuse their respective inputs; explicitly accepting private messages from anyone grants no host permissions. Automatic group reply decisions are enabled by default; the mention-only rule applies when that mode is disabled. The operator binding does not implicitly allow private chats.

Connection choices and admission policy persist separately from life history and restore under the same `DSH_HOME`. Saving connection choices or changing the token closes the old connection and drains its work before reconnecting. Disabling the connection closes its listener and QQ-owned Agents; life identity, conversation bindings and delivery receipts remain durable. Removing the token removes the provider-managed credential; inherited environment or explicit deployment credentials must also be removed to prevent fallback. Uncertain writes stop dependent work until verified storage is reloaded.

Only loopback WebSocket endpoints without URL credentials, query or fragment are accepted. For container clients, publish the OneBot endpoint onto loopback and use forward mode. The adapter authenticates with a Bearer token, verifies each frame's bot account and reconnects after a forward connection closes. It does not enable or configure the client's OneBot endpoint automatically. Other profiles can explicitly load this package's overlay beside Genesis and its life preset; upstream Harness defaults remain unchanged.

## Conversation preferences and workspace

In **QQ conversation preferences**, enter an additional prompt such as “Keep replies brief and natural, usually one to three sentences.” Save with the conversation policy. Changes apply to the next admitted QQ request, including an explicit logged clearing when the prompt is removed; Web conversations outside QQ do not receive it. These preferences do not grant permissions.

Default context windows are 200,000 tokens for ordinary private conversations, 400,000 for groups and 500,000 for the bound operator's private conversation. A group retains its group window when the operator speaks there. Automatic pressure compaction uses the smaller of the configured window and actual model capacity, with the existing threshold, reply reservation and headroom. These are history-management budgets, not a way to expand model capacity or guarantee exact token accounting. Failed summarization retains the existing visible history and reports a Host warning. QQ requests independently cap output, including reasoning, through the plugin deployment setting `maxCompletionTokens` (default 16,384); a smaller explicit request cap wins. At a 400,000 window, the default 80% pressure ratio and 65,536-token headroom yield a 318,080-token input threshold instead of 78,464 with a 256,000-token output reservation. Tools, images and system context count toward input pressure. This setting does not modify Web or memory-model output limits. After restarting an existing Session, its old logged output reservation can still cause one pre-request compaction; the next logged QQ request uses the new cap.

With the Web workspace registry loaded, QQ registers its dedicated directory as **QQ** and attaches conversations there. Stable bot account plus group or correspondent IDs identify Sessions; the title is the group name or private correspondent's current nickname. On each admitted incoming message, private nicknames refresh from the authenticated frame and group names refresh through OneBot `get_group_info`. Metadata failure preserves the current title or initially uses the numeric ID; a later message retries. Names do not change identity or grant operator authority.

QQ reuses a matching life Agent already opened by Web. Disconnecting QQ disposes only Agents owned by QQ; an Agent borrowed from Web remains open.

After a QQ Session is archived, the next admitted message from the same user or group creates a new Session while the old Session stays archived. The new binding is persisted before input admission; later messages and restarts use the latest binding. Person identity, relationships, long-term memory and historical Session ownership remain continuous; replayed old messages do not receive another reply. Unarchiving an old Session does not switch incoming messages back to it. To stop receiving messages, disable the QQ connection or remove the target from the allowlist. Proactive sending still refuses a target whose latest binding is archived until new input arrives or the operator restores that Session.

## Selective group replies and history

Enable **Let the decision model choose group replies** in Plugins → Genesis → QQ. The selected QQ decision model considers actual mentions, the latest five visible group messages, the authenticated speaker's relationship estimates, configured public character tendencies and interests supported entirely by this group. Affection and interest increase willingness without requiring a response; a mention can still be declined when it addresses someone else or a reply would interrupt. Private messages bypass this decision; input arriving during a reply joins the next model step together. Disable automatic decisions to use the existing mention-only rule or reply to all admitted group messages.

In **QQ reply decision model**, explicitly reuse the shared Genesis decision route, choose an existing registered provider/model, or configure a separate System One/TypeSafe endpoint, model and threshold (0–1). The dedicated write-only key uses `GENESIS_QQ_DECISION_API_KEY`; registered providers retain their own credential configuration. Saving QQ settings never changes memory decision settings or credentials. Independent version-1 settings and bounded recent receipts restore after restart. The recent list shows the source group/message ID, time, actual reply/skip/failure outcome, and genuine endpoint probability with its threshold. Generative boolean results show **Probability not provided**; failures do not become 0%. Refresh samples the latest receipts; it does not rerun decisions.

Decision requests receive a bounded page of the latest five visible messages. Normal replies supplement only unanswered observations from this window that are absent from retained context; reply-triggering input enters through the inbox, and previous replies already remain in the conversation. Deduplication derives from retained logged context across restart; compressed-away observations may be supplied again. Empty updates and repeated history-tool reminders are omitted. `recentMessages` changes the count; `historyChars` bounds each complete serialized page and `historyLimit` caps tool pages. Oversized text is explicitly marked truncated. Every decision request/response, observed group message and reply/skip/failure outcome is logged in that group's Session. A failed decision queues no reply and appears in QQ status; later messages may be evaluated normally.

Automatic recent-message context retains observed QQ message IDs for quoting and omits Session sequence numbers and pagination cursors. Model-facing participant relationships omit numeric confidence; internal relationship estimates and decision receipts retain their audit data. Speaker accounts, nicknames, times, message text and necessary attachment handles remain available. Explicit history-tool pages retain identifiers for pagination and message-reference tools; existing stored messages and audits are unchanged.

The innate `genesis_qq_history` tool reads only the caller's active, allowed QQ conversation, including older unanswered messages. Optional `limit` selects the page size; use `nextBeforeSeq` as the next `beforeSeq` to move backward. No group or Session selector is accepted. Private QQ conversations expose their own history; ordinary Web Sessions do not expose this tool. Execution rechecks channel policy and archival. Tool results use the normal logged pipeline and exclude tool arguments, results and hidden reasoning. It reads messages already observed and retained locally, not earlier messages from the QQ server.

Observations are flushed before inference and deduplicated by message ID across reconnects and restarts. Interrupted or failed decisions are not automatically replayed, including a crash between a recorded decision and reply enqueueing; inspect the original Session and send a new message if needed. Disabling QQ removes history-tool registrations. Deleting the original Session through the existing deletion workflow removes these observations and decision audits; forgetting a person alone does not erase the original dialogue. Queue and input capacity refusals are reported rather than silently retained.

## Images, video, files and quoted replies

Received image/sticker, video and file segments use the existing immutable attachment store. The normal reply receives normalized images only when its selected model declares image input, bounded UTF-8 document text, PDF text extracted with `pdftotext`, and video frames extracted with `ffmpeg` at 0, 5 and 10 seconds by default. PDF/video conversion requires the existing managed subprocess provider and an enforcing read-only sandbox. This is sampled visual information: no continuous video or audio transcription, OCR guarantee, Office/archive decoding or arbitrary executable processing. Unsupported formats, missing decoders, model limitations and rejected downloads produce visible notices; they do not become invented descriptions. Original files remain available by attachment ID when storage succeeded.

`genesis_qq_read_media` reads attachments already received or produced in the current conversation, even when the current message has no attachment. Supply exactly one `attachmentId` or a `messageId` whose original attachments were retained here; history pages expose attachment metadata separately from truncated text. A message lookup reads at most `maxMediaItems` attachments and never fetches arbitrary remote messages. If an old attachment was not retained or its bytes were removed, ask the sender to resend it. `genesis_qq_send` sends such an image, sticker image, video or file, sends a numeric QQ face emoji, or quotes an observed numeric `messageId` with reply text. It accepts no recipient, Session, arbitrary URL or host path. Current channel permissions and archival are checked again before sending. Animated stickers use original image bytes rather than normalized stills. Support for file uploads, sticker rendering and media downloads depends on the OneBot client's actions; [NapCat's file guide](https://napneko.github.io/develop/file) describes its client configuration. File upload acknowledgements without message IDs remain **uncertain** and must not be automatically retried.

Inbound quotes retain the original message ID, speaker and excerpt, separately from the authenticated current sender. After verifying the same route, uncached quoted media is admitted under the existing download limits; its references remain available to the read tool. The adapter uses local history first, otherwise fetches through `get_msg` and verifies the same group/private route before admitting content; unverifiable or cross-route content is withheld. File notices without a numeric QQ message ID receive stable synthetic source IDs and cannot be quoted as ordinary messages. Quotes, decoded file contents and filenames are untrusted evidence, never identity proof or operator authorization. Recent-message/history pages retain attachment references even for unanswered group messages; the decision model sees these bounded labels, not automatic image/video interpretation.

Deployment configuration bounds admission: `maxMediaItems` defaults to 5, `maxMediaBytes` to 20 MiB per attachment, `mediaTextChars` to 12,000 and `mediaTimeoutMs` to 30 seconds. Existing attachment image-count/byte limits also apply. `videoFrames`, `videoFrameInterval`, `videoFrameSize`, `ffmpeg`, `pdftotext` and `mediaGraceMs` configure fixed conversion. `mediaOrigins` accepts exact HTTP(S) origins or a leftmost `*.` subdomain wildcard with the same scheme and port. Defaults include `https://*.qq.com`, the exact `https://multimedia.nt.qq.com.cn`, and the QQ picture origins in the configuration catalog; add a different client download origin explicitly. An HTTP media URL is upgraded to HTTPS only when its HTTPS origin is already allowed; this adds no new allowed host. Rejection notices name the origin or file-ID restriction without exposing full download URLs. Redirects, URL credentials and client-local paths are refused. Base64 bytes may be supplied directly by the authenticated client, subject to byte and WebSocket-frame limits. Downloads send no stored model/OneBot credential. Session logs retain references and decoded model-visible data, not bearer download URLs or duplicated base64 payloads.

Disabling QQ unregisters its media tools and drains or cancels outstanding work. Deleting the original Session removes quote/media audits and model-visible excerpts; attachment blobs follow the existing shared attachment-store retention/deletion policy and are not removed merely by forgetting a person. Dedicated decision-key removal uses the settings credential action. For complete erasure, also remove the QQ decision domain's recent receipts (`genesis_qq_decision`) through the operator's storage deletion workflow and the relevant attachment objects after checking other references.

## People and relationships

Internal `PersonId` values derive from the QQ account ID and remain Host attribution keys. New model-facing speaker headers and participant records use `qq`, current `nickname`, recorded `name` (or null), `seenBefore` and `isOperator`. The same account remains recognizable on its first message in another group, including after a nickname change; these labels are not proof of a legal name, familiarity or trust. New people are strangers with no retained relationship profile. A meaningful, cited exchange can establish a profile; familiarity, affection, trust, felt security and attachment evolve independently with per-field confidence. Being familiar does not imply being trusted. Merely mentioning or forwarding another person cannot change that person's relationship.

The bounded participants context includes actual recent speakers and their current estimates. Repeated exchanges are attenuated per person. `people.maxPeople`, `maxEvidence` and `maxChanges` bound retention and appraisal; exhaustion refuses changes visibly. [Data records](data-model.md) defines persistence. Existing operator estimates transfer only after an explicitly bound operator message; nickname matching cannot establish operator identity. In the bound operator’s private conversation, logged `participants.operator.qq` links the authenticated account to the configured operator name and identity. In groups, the matching speaker receives the configured name, such as “妈妈”, and `isOperator: true`, while the private identity description remains empty. Another account using the same nickname cannot acquire that binding. Recent speakers are selected before older ones when the participant budget is full; omissions are counted. Forgetting a person clears retained identity recognition up to that deletion marker.

## Mentions

Incoming OneBot mention segments and CQ-string mentions retain their numeric targets as `@QQnumber`, including messages consisting only of mentions. The logged channel context identifies the bot account. Mentioned accounts are distinct from the authenticated sender; mentioning someone never transfers their identity or authority.

In group replies, standalone numeric handles such as `@12345` become real OneBot `at` segments, and QQ displays the target's name. Nickname mentions, email addresses and raw CQ text remain literal text; outbound `@all` is unsupported. Private replies keep handles as text. Reply splitting counts Unicode text and the numeric mention spelling, and never splits a mention target. Every outgoing part still requires its own confirmed message ID; unknown outcomes are never automatically retried.

## QQ toolkit permissions

**Settings → Toolkits → QQ tool permissions** configures allow/deny rules for a QQ account (`person`) or an entire group (`group`). Rules accept an exact tool name, a trailing prefix wildcard or `*`. Matching person rules override group rules; within one scope, longer prefixes win and an exact name overrides the same prefix. Unmatched tools keep the default policy below. An allow rule exposes learned or innate QQ tools without toolkit activation and can permit full browser operations; it never installs or teaches tools, grants operator identity, changes conversation admission or bypasses provider authorization, sandbox and approval checks. Operator private conversations retain Web permissions. Tool declarations can remain visible to other speakers; each execution checks the current authenticated speaker and current policy, so revocation applies immediately.

Only the operator can ask the AI to change these rules, for example “Allow QQ 12345 to use mcp__playwright-mcp__browser_evaluate” or “Deny group 67890 access to computer”. The innate `genesis_qq_permissions` tool supports `list`, `set` and `remove`; changes require the revision returned by `list`. Removing a rule restores the remaining matching rules or defaults. A group grant cannot delegate permission management. Confirmed rules survive restarts in the independent version-one `genesis_qq_permissions` domain; stale edits are refused, and damaged data or uncertain writes stop dependent authorization until verified reload.

In the bound operator’s private QQ conversation, tool permissions match authenticated Web conversations: all toolkit entries are discoverable and can be activated regardless of `qqAccess`. Learning, conversation-local toolkit activation, sandbox, approval and provider checks still apply. The following default QQ audience restrictions apply to groups and other private conversations without a matching permission override.

In **Settings → Toolkits**, enable **Allow this toolkit on QQ** for each intended toolkit. The new permission starts as **Require the authenticated operator to enable and use it**; uncheck that restriction to allow anyone. Disabled toolkits stay unavailable on QQ. Existing catalogues migrate as disabled; saved catalogue rows use version 2 and restore alongside version-one catalogues. API/config entries use optional `qqAccess: disabled | anyone | operator`.

Registered `web_search`, `web_fetch` and `genesis_speech` are available to ordinary speakers without learning or toolkit activation, under the providers' query, output and network limits. Speech requires configured provider credentials and may incur charges; generate audio, then send its attachment with `genesis_qq_send(kind="file", asVoice=true, attachmentId=...)`. New catalogues also include “网页浏览” (`browser-reading`) with `qqAccess: anyone`: after learning and conversation-local activation, ordinary speakers may use Playwright `browser_navigate`, `browser_snapshot`, `browser_take_screenshot` and `browser_wait_for`. Other Playwright, Chrome DevTools and Stagehand operations remain unavailable to ordinary speakers even through a broadly permitted toolkit. Navigation accepts only HTTP(S) URLs without embedded credentials; browser output cannot specify `filename`. This excludes direct script execution, form input, file transfers and tab management. Browser ownership follows the provider: the workspace's persistent browser shares pages and login state across conversations; this permission does not isolate them. Disable QQ browser access when that state must remain private. Saved catalogues are preserved; add an exact-member browsing toolkit or change an existing toolkit's audience to opt in.

Members still need to be learned and registered. `genesis_toolkit` lists eligible toolkits and activates them only in the current conversation. Anyone can close a toolkit. Operator-only activation requires the current actual speaker's configured QQ account, and each protected member execution rechecks that speaker as well; another member cannot borrow earlier operator approval. Names, @ targets, quotes, relationships and retrieved history cannot grant operator authority. Permission or membership edits revoke execution immediately. Previously injected registered tool declarations remain present across speaker and permission changes; unauthorized calls return errors. Explicit toolkit closure removes its declarations unless another active toolkit contains them. Context compaction preserves tool declarations. Eligible tools omitted by earlier compactions return automatically on the next request, including after reopening the Session; learning and toolkit activation do not need to be repeated. Learned-tool context uses the same selection as declarations. Execution denials distinguish a missing current operator, missing learning and missing QQ toolkit access. Forked Sessions do not inherit activation; reopening the same Session replays versioned grants from its audit. Old activation records without a QQ grant cannot unlock protected tools.

Sandbox, tool approvals and provider permissions still apply independently. Removing the last toolkit containing a learned tool does not expose that tool on QQ; a remaining explicit QQ permission or innate declaration is required. Host files and shell therefore remain closed by default. Learned `genesis_record` and `genesis_tasks` are operator-only exceptions that need no toolkit activation: QQ advertises them and executes them only while the current authenticated speaker is the bound operator. Other accounts cannot read or write personal records or inspect, create or control workspace tasks. The bound operator’s private conversation uses the Web rules described above.

## Cross-conversation messages

`genesis_message` lets the currently authenticated, bound operator find recipients, send text, forward their own original text and inspect receipts. It requires no tool learning or toolkit activation. Ordinary speakers cannot execute it, including through direct tool calls. Incoming admission and outbound permission are separate: `acceptPrivateFromAnyone` grants no outbound targets. Configure `outboundGroups` and `outboundUsers` on the QQ plugin; both default to empty. For example, save this as an operator patch and apply it after the QQ overlay with `pnpm dsh web --patch <file>`:

```yaml
- id: genesis-qq
  config:
    cwd: !!js dshHomePath('qq-workspace')
    outboundGroups: ['67890']
    outboundUsers: ['99999']
```

Replace the sample accounts with intended destinations. `targets` intersects these lists with the live platform group/friend directories and supports name/account search plus `offset` pagination. Names are untrusted labels; use a returned exact `target`, asking the operator when their description is ambiguous. A clear request with an unambiguous destination needs no additional confirmation. `send` accepts `target` and `text`. `forward` accepts `target` and an observed `messageId` from the source conversation; only the operator's own pure-text message is supported, with a sender header and its body preserved verbatim. The bounded source projection retains the most recent `historyLimit` original messages; resend older text when it is outside that window. Attachments, platform mentions and cross-conversation source-message lookup are not forwarded. Outbound text uses literal text segments, so copied CQ codes and @handles do not become platform commands.

A target need not have spoken before or have an active Agent. Sending opens or resumes its stable Session without submitting a model task; archived conversations remain paused. The source and destination logs receive the exact delivery plan before any external write. A confirmed delivery additionally adds a logged notice to the target conversation without triggering another reply. The independent version-1 `genesis_qq_messages` domain stores receipt identities, source/target references, content hashes and acknowledgements, without a second message-text archive. `maxMessageReceipts` defaults to 10,000; exhaustion refuses new sends without evicting deduplication evidence. Each result counts its complete JSON against `historyChars`; long acknowledgement lists report omitted IDs.

`status` accepts a returned delivery `id` from the same source conversation. `confirmed` means every chunk received a QQ message ID, not that anyone read it. `uncertain` includes interrupted reservations, missing acknowledgements and partial delivery. Repeated identical requests within one operator message reuse their receipt, including across repeated tool calls. Restart never automatically sends journal entries again. A later explicit operator request is a new action. If the platform confirms delivery but a later audit write fails, inspect `status` before deciding what to do. Keep this journal with the same life and source Sessions; deleting it independently destroys replay protection. Message-content deletion requires removing the applicable source and target Sessions; complete life deletion also includes this journal.

When the [AI companion integration](../../packages/experimental/genesis-companion/README.md) is enabled, the same `genesis_message` target list also includes its persistent internal conversation. Its sleep checks, explicit-text delivery, bounded replies and source-scoped receipts are owned by that integration; QQ allowlists and platform confirmations retain their existing meaning.

## Memory and delivery

The life overlay selects `memorySharing: life`, sharing stored long-term and unexpired temporary memories across Web, private QQ conversations and groups. Original attribution remains attached to the same life; it does not identify every speaker as the operator or expose arbitrary Session history. Set `memorySharing: conversation` on the Genesis plugin to restore source-audience isolation, which remains the standalone-plugin default. In that mode, private-message memories are available only in private conversations with the same person. Group memories stay in that group conversation. Mixed-source interpretations must satisfy every source restriction. Legacy operator memories remain operator-private, while configured initial character tendencies can be shared. These rules apply before prompt selection, semantic ranking, association and explicit `genesis_recall`; model wording is not the access check.

QQ Sessions include `genesis_recall` under the selected memory policy, current-conversation `genesis_qq_history`, scoped media tools when attachment storage is available, and registered `web_search`/`web_fetch`/`genesis_speech` by default without teaching or activating a toolkit. When configured and already learned, `genesis_record` and `genesis_tasks` are available on QQ for the bound operator's authenticated turns. Deployment `qqBasicTools` explicitly defines the innate names. Private plans and interests from other conversations are omitted. Use the authenticated local Web interface for operator management. Memory sharing is deployment-owned; no per-memory sharing editor is provided.

Incoming message IDs and outgoing Session event sequences are reserved durably before admission or sending. Confirmed delivery requires a OneBot message ID for every text chunk. An interrupted or partially acknowledged delivery remains uncertain and is not automatically resent after restart. Inspect the original Session and `qq.receipt` life events before any manual retry. The same life identity and conversation Session resume after restart; unreadable published Sessions fail instead of starting a replacement conversation.

The host-only `LifeCore.forgetPerson` API removes the retained relationship and memories sourced from that person's messages. It retains audited life events and original Harness Sessions; complete account-data erasure also requires the operator's existing life and Session deletion workflow.

## Limitations

This adapter supports reactive conversations and explicit in-conversation media delivery. It does not accept friend requests, send proactive QQ contacts or expose a relationship-management GUI. Other plugins' channels and operator Web behavior retain their own permissions. Local automated tests use a scripted model and a OneBot peer; a real QQ login and message exchange require the operator's logged-in client.
